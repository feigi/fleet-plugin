# The Label map: label strings are derived from the consumer repo; shipped names are roles and defaults

Date: 2026-10-15
Status: spec, input to `/to-tickets`.
Relates to: `docs/specs/2026-07-30-fleet-trust-the-label-design.md` § Out of scope "Label-remap coupling" (closed by this spec); `.out-of-scope/consumer-label-spelling-alias.md` (#2883 — its reopen condition is met; retired by this spec); ADR 0015 (the Recipe cache, the pattern this follows); ADR 0013 § 4 and ADR 0032 (which roles are written where — unchanged); ADR 0019 (shipped files cite nothing); `docs/requirements.md` § 2.4.
Depends on: nothing.
Base tree: `main` at `5fd997c3` (2026-10-15).

## Problem Statement

A consumer repository that names its triage labels differently from the five canonical role names — the renaming `/setup-matt-pocock-skills` Section B explicitly offers and records in `docs/agents/triage-labels.md` — cannot run the fleet. Every script and runbook in the shipped surface types the canonical strings: the Shortlist query asks for `ready-for-agent` and excludes `in-progress`, `onhold`, `wontfix`, `needs-triage`, `needs-info`; the claim writes `in-progress`; the finisher writes `ready-to-merge` and the merge bot reads it; review deferrals file `needs-triage`; the cockpit's pool query and the tick's claimed-count read their own copies. Against a repo whose label is `agent-ready`, the Shortlist query matches nothing and the controller reads "no work" — silently, because an empty answer is a valid answer. A repo whose hold label is `on-hold` (#2883) sees the fleet pull tickets the maintainer froze. The only remedy today is "rename your labels to ours", which the pre-flight enforces for three of the eight and the requirements document demands for all.

## Solution

The plugin stops typing label strings. Every label the fleet reads or writes is a **Label role** — the eight names `needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`, `in-progress`, `onhold`, `ready-to-merge` — and a **Label map** gives the string the consumer's tracker uses for each role. The map is derived from the repository the way the Recipe is: read from what the repo already declares (`docs/agents/triage-labels.md`) and what its tracker already has (the live label list), cached as fleet state beside the Recipe cache, read by every script and runbook, and never inferred at read time. Where derivation is certain, nothing is asked. Where it is not — no table, a table naming a label the tracker lacks, a near-miss spelling, or nothing found at all — the maintainer is asked once, on the first run, with a suggestion per role and the role name itself as the default when nothing was found; on confirmation the fleet creates any label the answer names that does not exist yet, then caches the map. Every later run reads the cache. A consumer whose labels are the defaults notices nothing except that the requirements no longer tell them to create the canonical strings.

## User Stories

1. As a fleet maintainer whose tracker uses `agent-ready` instead of `ready-for-agent`, I want the fleet to shortlist my `agent-ready` tickets, so that I can run the fleet without renaming labels my team already uses.
2. As a fleet maintainer whose labels are exactly the canonical names, I want the first run to derive the map without asking me anything, so that the default setup stays zero-config.
3. As a fleet maintainer, I want the derivation to read the `docs/agents/triage-labels.md` table `/setup-matt-pocock-skills` wrote, so that one file declares my vocabulary for the triage skill and the fleet alike.
4. As a fleet maintainer whose repo has no `docs/agents/triage-labels.md` and none of the canonical labels, I want the first run to ask me once, suggesting the eight default names, so that I can accept them in a word and have them created.
5. As a fleet maintainer whose repo has `on-hold`, I want the first-run question to suggest `on-hold` for the `onhold` role (a near match), so that I confirm rather than retype.
6. As a fleet maintainer, I want the question to list every uncertain role at once with its suggestion, where the suggestion came from, and the alternatives found, so that one answer settles the run.
7. As a fleet maintainer, I want a label I confirmed but the tracker lacks to be created only after I confirmed it, so that the fleet never invents labels in my repo on its own.
8. As a fleet maintainer, I want to be told, in the same reply, how to make the answer permanent (edit `docs/agents/triage-labels.md`), so that a fresh clone or a teammate's machine derives the same map without being asked.
9. As a fleet maintainer who renamed a label after the map was cached, I want the pre-flight to fail naming the role and the missing string, so that a stale map is caught before any dispatch.
10. As a fleet maintainer, I want deleting `.fleet/labels.json` to force a fresh derivation on the next run, so that the recovery is the same as for every other fleet-state file.
11. As a fleet maintainer who edits the `docs/agents/triage-labels.md` table after the map was cached, I want the next run to re-derive from the new table, so that the committed file wins over the cache.
12. As the run-team controller, I want the Label map derivation step to run in phase 0 before the pre-flight and before any claim, so that no member ever runs against an absent or stale map.
13. As the run-team controller, I want to type the mapped string wherever a runbook names a role in a `gh` command, so that relabel-by-cause, filing and claim release work on a remapped repo.
14. As a solo developer running `/next-ticket`, I want the candidate list and the claim to use the map, and the derivation step (question included) to run before the first query, so that the solo flow matches the fleet's.
15. As a fix-applier running `/review-and-fix` standalone, I want deferrals filed under the repo's `needs-triage` string, so that triage finds them.
16. As a fix-applier or finisher dispatched by the fleet, I want to read the map and never be asked anything, so that a member with no channel to the maintainer never stalls on a question.
17. As a merge bot, I want to read the repo's `ready-to-merge` string from the map in every poll and gate, so that a renamed merge label still queues PRs.
18. As a cockpit operator, I want the pool column and the READY state to read the mapped strings, so that the cockpit shows the same work the controller sees.
19. As a plugin maintainer, I want every script that reads or writes a label to resolve the role through one shared reader, so that there is one place a role becomes a string.
20. As a plugin maintainer, I want a script run where no map exists to refuse and name the derivation step, so that a remapped repo can never silently read as "no work".
21. As a plugin maintainer, I want the map writer to refuse a string that cannot be queried safely (a double quote or a backslash, GitHub's length limit, two roles sharing one string), so that the Shortlist query cannot be broken by a confirmed answer.
22. As a plugin maintainer, I want the five `wayfinder:*` and the three release labels left as they are, so that this change covers the labels the fleet owns and nothing another skill owns.
23. As a triage-skill user, I want the fleet's reading of `docs/agents/triage-labels.md` to follow the skill's own rule ("when a skill mentions a role, use the string from this table"), so that the two agree by construction.
24. As a maintainer of this repository, I want its own run to derive the identity map with no question, so that dogfooding is unchanged.

## Implementation Decisions

**D1. Vocabulary (two glossary entries, `CONTEXT.md` § Consumer repo).**
- *Label role*: a name the fleet's scripts and runbooks use for a label's meaning — the five triage roles plus `in-progress`, `onhold`, `ready-to-merge`. A role is never typed into a `gh` command; its name is also its default string. Avoid: label, canonical label, constant.
- *Label map*: the fleet-state record mapping every Label role to the string the consumer's tracker uses, derived from the repository's triage-label table and its live label list, confirmed by the maintainer where derivation is uncertain, read by scripts and runbooks. Absent means "derive", never "infer". Avoid: label config, vocabulary file, alias, `labels.json` (as a term).

**D2. Scope: the eight roles.** `wayfinder:*` stays literal (mandated by the external `/wayfinder` skill; negating an absent label is a measured no-op). `patch`/`minor`/`major` stay literal (release segments; the finisher already answers `undefined-in-repo` from the live list). Exactly one string per role — no aliases, no second spelling.

**D3. The cache.** `.fleet/labels.json`, resolved through the shared fleet-dir resolver like the Recipe cache, so a worktree and the main checkout name the same file. Content: `derivedAt` (ISO time), `table` (what the triage-label table said when derived: `present` and its `rows` role→string, so a changed table is detected without the network), `roles` (all eight role→string), `origin` per role: `table` | `default` | `maintainer`. Gitignored with the rest of `.fleet/`; never committed; never written by hand.

**D4. One module, three verbs, plus a reader.** A new script module `label-map` (the Resolver reaches it like every sibling) owning the cache's format:
- `ensure` — the **Label map derivation step**. Reads the cache; valid (parses, all eight roles present, strings valid per D8) and its `table` equals the table now in the repo → prints the map, exit 0, no network. Otherwise derives (D5): every role certain → writes the cache, prints the map, exit 0; any role uncertain → prints the question payload (D6) and exit 3, writes nothing, creates nothing. Exit 2: not a repository, or `gh` could not answer (the live list is required to derive).
- `set [--accept-suggestions] [--create] [<role>=<label> …]` — writes the map from a fresh derivation plus the maintainer's answer: explicit pairs win, `--accept-suggestions` fills every remaining uncertain role with its suggestion, any uncertain role still uncovered is a refusal naming it (exit 1). Each confirmed string that does not exist live is created with `gh label create <string>` only under `--create` (an "already exists" answer counts as existing; no colour is passed); without `--create` a missing string is a refusal naming it. Writes only when every mapped string exists live. Exit 0 prints the map.
- `show [<role>]` — prints the mapped string (one role) or the whole `roles` object (no role). Exit 1 with no cache or an invalid one, the message naming `ensure` as the derivation step. Exit 2 unknown role / not a repository.
- `verify` — reads the map and the live label list; exit 0 when every mapped string exists, exit 1 naming each missing `role → string`. The pre-flight's probe (D10).
- The reader is an exported function the scripts import (D9): returns the `roles` object or throws a typed error whose message names the derivation step. No defaults at read time — the user's ruling.

**D5. Derivation, per role.** Inputs: the table (D7) and the live label list (`gh label list --limit 1000 --json name`; a list that fills the limit is exit 2, the capped-list rule every list read here follows). Verdicts:
- *certain* — the table has a row for the role and its string exists live (origin `table`); or the table has no row and the role's default (its own name) exists live (origin `default`).
- *uncertain* — everything else: a table row whose string is not live; no row and the default not live; two table rows for one role with different strings. For an uncertain role the suggestion is, in order: the table's string if a row exists; else the unique live *near match* (same string after lowercasing and dropping every non-alphanumeric character — `on-hold` ≈ `onhold`, `Ready For Agent` ≈ `ready-for-agent`); else, with several near matches, the alphabetically first; else the role's default. Every near match is listed as a candidate.
- Certainty never comes from a near match alone: a near match is a suggestion, which is what "ask when not absolutely sure" means.

**D6. The question.** `ensure` exit 3 prints one JSON object: `certain` (role→string already settled), `uncertain` (array of `{role, suggestion, origin: "table"|"near-match"|"default", candidates: [live near matches], exists: bool}`). The asking entry point (D11) renders it as one question listing each uncertain role, its suggestion, why (`declared in docs/agents/triage-labels.md but not in the tracker` / `near match in the tracker` / `nothing found — the default, to be created`), the alternatives, and ends with: reply `defaults` to accept every suggestion, or name `<role>=<label>` for any you want otherwise; labels that do not exist are created on your confirmation. After writing, the reply tells the maintainer how to make it permanent: add or edit the row in `docs/agents/triage-labels.md` (first cell the role, second the string). The plugin never writes that file.

**D7. The table.** `docs/agents/triage-labels.md` under the current checkout's top level. The table read is the one whose second header cell, backticks and whitespace stripped, is `Label in our tracker` — the header `/setup-matt-pocock-skills` seeds; any other table in the file is not read (this repository's second table, `Labels that are not triage roles`, has an `onhold` row whose second cell is a description, not a label). In it, a row is any markdown table line whose first cell, backticks and whitespace stripped, is one of the eight role names; the second cell, stripped the same way, is the string. Header and separator rows never match. The five-row seed `/setup-matt-pocock-skills` writes is read as-is; a consumer may add rows for `in-progress`, `onhold`, `ready-to-merge` and they are honoured the same way. An empty second cell is no row. File absent → `table.present = false`.

**D8. Valid strings.** Non-empty after trimming, at most 50 characters (GitHub's limit), no `"` and no `\` (the Shortlist query cannot represent them — the existing `--require-label` refusal), and no two roles mapping to one string. `set` refuses otherwise, naming the role and the rule.

**D9. Every script resolves roles through the reader; no caller passes strings.** The scripts that change, and what each does with the map:
- the candidates scan: the exclusion clause, today the static literal `EXCLUDE` that no caller assembles, becomes a function of the map: the mapped `in-progress`, `onhold`, `wontfix`, `needs-triage`, `needs-info` are quoted in `query()` — the call site the `EXCLUDE` comment names as the home of a quote-everything rule, which today quotes only the `--require-label` value — and the five `wayfinder:*` clauses stay literal and unquoted as they are today; the comments at `EXCLUDE` that call it a static literal no caller assembles are rewritten with it. `--require-label` now names a **role** and is resolved through the map — an unknown role is a usage refusal (exit 2); both callers already pass `ready-for-agent`, so neither changes.
- the shortlist, the cockpit's pool gather, the tick's claimed count, the stranded scan: the role they read replaces the constant.
- the board compute, the tick's queued set, the merge gate, the finisher's label script: `ready-to-merge` resolved through the map for every read and the one write.
- the dispositions check: the `needs-triage`/`ready-for-agent` home ordering and the `wontfix` record test compare against mapped strings; the row table keeps roles.
- the three shell scripts (claim, release, drop-merged-label): obtain the string once via `label-map show in-progress` through their sibling-script directory, refuse with its message when it refuses, and use it in every `gh issue edit` and every label scan; their dry-run `would:` lines print the string.
- stderr and receipt text may name the role (`in-progress: still on the issue`); a `gh` argument, a label comparison, and any text written to the tracker use the string.

**D10. The pre-flight.** The three per-label rows become one row, `label-map`, whose probe is `label-map verify`; the marker hash folds in the map's `roles` pairs, so a re-derived map is checked once more and an unchanged one is skipped as today. An absent map fails the row with `verify`'s message, which names `ensure`.

**D11. Entry points and the ask.** The Label map derivation step is `ensure`, then — on exit 3 — the question (D6) and `set --create` with the answer, then `ensure` again, which now exits 0.
- `/run-team` phase 0: after the instruments pin and the main-checkout baseline, before the pre-flight. Exit 3 → ask the maintainer and wait; nothing in the run — no pre-flight, no Shortlist, no Pull, no dispatch — proceeds until the map is written. This is the controller's own step, once per run start at most.
- `/next-ticket`: step 1, before the candidates query. The `gh label create in-progress …  # first time only` line leaves: creation is the derivation step's, on confirmation.
- `/review-and-fix` standalone: before its step 1. Dispatched as a fix-applier, and every other dispatched member (implementers, finishers, the merge bot): never `ensure`, never ask; `show`/the reader only, and a refusal is reported to the controller as a halt cause, like a Recipe-cache refusal.
- The merge bot's monitor shell snippet and every `gh … --label` in shipped prose read the string via `label-map show <role>` or type the string the map printed; the prose rule stated once near the top of each shipped runbook/command/agent that names a label: *label names in this file are roles; the Label map gives the string to type; a member never derives the map.*

**D12. Documents.** A new ADR (next free number) rules: the eight labels are roles; strings come from the consumer repo into fleet state; shipped surface names roles only; the plugin writes no consumer file; it names `.out-of-scope/consumer-label-spelling-alias.md` as superseded (the note is deleted, its "Prior requests" line moved into the ADR's Context) and the 2026-07-30 spec's "Label-remap coupling" item as closed (annotate that item in place, a one-line `Closed by ADR NNNN` — the dated spec is otherwise left as written). `docs/requirements.md` § 2.4 is rewritten: the eight roles, defaults equal to the role names, how a repo with other names declares them (the table) or answers once, that missing labels are created on confirmation, and that the check loop is replaced by the pre-flight's `label-map` row. A component doc for the Label map mirrors the Recipe's. This repo's `docs/agents/triage-labels.md` gains one sentence: the fleet reads this table. Shipped prose, comments and runtime strings cite none of these (ADR 0019).

**D13. Not changed.** Which role is written where — ADR 0013 § 4's relabel-by-cause table, ADR 0032's filing rule, the finisher's `ready-to-merge` discipline, the Shortlist's exclusions — none moves; only the string typed for each role does.

## Testing Decisions

A good test drives a script's CLI as a child process against a fake `gh` on `PATH` and a temporary git repository, and asserts exit code, stdout payload and the `gh` argv the stub recorded; it never imports internals or pins a comment. Prior art: the candidates scan's stub that answers `--jq` from a fixture file, the pre-flight's row probes, the finisher's label receipt tests, the fleet-dir resolver tests.

Seams (one new, the rest existing):
1. **New — the `label-map` CLI.** Fixtures: temp git repo with/without `docs/agents/triage-labels.md`; a `gh` stub answering `label list` from a fixture list and recording `label create`. Cases: identity table + all live → certain, cache written, origin `table`; a file holding the identity table plus a second table whose `onhold` row's second cell is a description → that row not read, no exit 3, and the map is the identity map (this repository's own file is that shape); no table + defaults live → certain, origin `default`; no table, nothing live → exit 3, every role suggested as its default with `exists: false`; table maps `ready-for-agent`→`agent-ready` but `agent-ready` not live → exit 3, suggestion `agent-ready`, origin `table`; `on-hold` live, no table → `onhold` uncertain with near-match suggestion `on-hold`; two near matches → alphabetical first suggested, both as candidates; `set --accept-suggestions --create` creates exactly the missing strings (argv recorded), writes the cache, `ensure` then exits 0 without a `gh` call; `set` without `--create` refuses a missing string; `set` refuses `"`, `\`, >50 chars, duplicates, an unknown role, an uncovered uncertain role; cached map + table edited → `ensure` re-derives; cached map + table unchanged → no `gh` call; `show in-progress` prints the string; `show` with no cache exits 1 and the message names `ensure`; `verify` with a mapped string deleted live exits 1 naming `role → string`.
2. **Existing script seams, one case each that proves the string flows:** with a map where `ready-for-agent`→`agent-ready` and `in-progress`→`wip`, the candidates scan's recorded search query carries `label:"agent-ready"` and `-label:"wip"`; the claim script's recorded `gh issue edit` carries `--add-label wip`; the finisher's write and read-back use the mapped `ready-to-merge`; the merge gate reads `label-pulled` against the mapped string; the dispositions check accepts a home labelled with the mapped `needs-triage`; the pre-flight's `label-map` row fails naming the missing role when `verify` fails, and its marker hash changes when the map does. Every existing test fixture that spawns one of these scripts seeds the identity map into its `.fleet/` through one new shared test-support helper — fixtures write the Recipe cache inline today, and `tests/support` holds no seeder for it.
3. **Prose pins (content, not modality — ADR 0017):** each shipped runbook/command/agent that names a label carries the one-sentence role rule; `/run-team` phase 0 orders the derivation step before the pre-flight; `/next-ticket` no longer creates `in-progress` itself; member definitions never run `ensure`.

Existing tests that pin the literal exclusion string, the three pre-flight label rows, or `gh label create in-progress` in `/next-ticket` are rewritten to the new behaviour, not preserved.

## Out of Scope

- `wayfinder:*` and `patch`/`minor`/`major` (D2).
- Writing or creating `docs/agents/triage-labels.md` in a consumer repo; the plugin reads it only.
- Aliases — two strings for one role — and a configurable *set* of roles; the eight are fixed.
- Deriving the map by agent reasoning (a deriver member): the sources are a table of known shape and a label list, so a script derives and the maintainer decides; no new agent.
- Live re-validation on every script read: the pre-flight validates once per map version; a label deleted mid-run surfaces as the `gh` write's own failure.
- Any change to which role is written where (D13).

## Further Notes

- This repository derives the identity map with no question: its table is the five identity rows and all eight labels exist, so the first run after this lands is the dogfooding check.
- `ensure` is a file read when cached and matching; the only network cost is one `gh label list` per derivation, plus the pre-flight's one `verify` per map version — well under the three `gh label list --search` calls the pre-flight makes today on a fresh marker.
- The Recipe precedent decides the shape: cache under `.fleet/`, scripts read and refuse when absent, derivation is an explicit phase-0 step. The one deliberate difference is who decides when derivation is uncertain — the maintainer, by a question, not a deriver agent — because a label vocabulary is a convention only the maintainer can rule on.
