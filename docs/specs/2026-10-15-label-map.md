## Problem Statement

A consumer repository that names its triage labels differently from the five canonical role names — the renaming `/setup-matt-pocock-skills` Section B explicitly offers and records in `docs/agents/triage-labels.md` — cannot run the fleet. Every script and runbook in the shipped surface types the canonical strings: the Shortlist query asks for `ready-for-agent` and excludes `in-progress`, `onhold`, `wontfix`, `needs-triage`, `needs-info`; the claim writes `in-progress`; the finisher writes `ready-to-merge` and the merge bot reads it; review deferrals file `needs-triage`; the cockpit's pool query and the tick's claimed-count read their own copies. Against a repo whose label is `agent-ready`, the Shortlist query matches nothing and the controller reads "no work" — silently, because an empty answer is a valid answer. A repo whose hold label is `on-hold` (#2883) sees the fleet pull tickets the maintainer froze. The only remedy today is "rename your labels to ours", which the pre-flight enforces for three of the eight and the requirements document demands for all.

## Solution

The plugin stops typing label strings. Every label the fleet reads or writes is a **Label role** — the eight names `needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, `wontfix`, `in-progress`, `onhold`, `ready-to-merge` — and a **Label map** gives the string the consumer's tracker uses for each role. The map is derived from the repository the way the Recipe is: read from what the repo already declares (`docs/agents/triage-labels.md`) and what its tracker already has (the live label list), cached as fleet state beside the Recipe cache, read by every script and runbook, and never inferred at read time. Where derivation is certain, nothing is asked. Where it is not — no table, a table naming a label the tracker lacks, a near-miss spelling, or nothing found at all — the maintainer is asked once, on the first run, with a suggestion per role and the role name itself as the default when nothing was found; on confirmation the fleet creates any label the answer names that does not exist yet, then caches the map. Every later run reads the cache and checks each cached string against the tracker's live list; a role whose label has gone from the tracker is asked about again. A consumer whose labels are the defaults notices nothing except that the requirements no longer tell them to create the canonical strings.

## User Stories

1. As a fleet maintainer whose tracker uses `agent-ready` instead of `ready-for-agent`, I want the fleet to shortlist my `agent-ready` tickets, so that I can run the fleet without renaming labels my team already uses.
2. As a fleet maintainer whose labels are exactly the canonical names, I want the first run to derive the map without asking me anything, so that the default setup stays zero-config.
3. As a fleet maintainer, I want the derivation to read the `docs/agents/triage-labels.md` table `/setup-matt-pocock-skills` wrote, so that one file declares my vocabulary for the triage skill and the fleet alike.
4. As a fleet maintainer whose repo has no `docs/agents/triage-labels.md` and none of the canonical labels, I want the first run to ask me once, suggesting the eight default names, so that I can accept them in a word and have them created.
5. As a fleet maintainer whose repo has `on-hold`, I want the first-run question to suggest `on-hold` for the `onhold` role (a near match), so that I confirm rather than retype.
6. As a fleet maintainer, I want the question to list every uncertain role at once with its suggestion, where the suggestion came from, and the alternatives found, so that one answer settles the run.
7. As a fleet maintainer, I want a label I confirmed but the tracker lacks to be created only after I confirmed it, so that the fleet never invents labels in my repo on its own.
8. As a fleet maintainer, I want to be told, in the same reply, how to make the answer permanent (edit `docs/agents/triage-labels.md`), so that a fresh clone or a teammate's machine derives the same map without being asked.
9. As a fleet maintainer who renamed or deleted a label after the map was cached, I want the next run's derivation step to find the cached string gone from the tracker and ask me again for that role — never suggesting the vanished string back — so that a stale map is caught before the pre-flight and any dispatch.
10. As a fleet maintainer, I want deleting `.fleet/labels.json` to force a fresh derivation on the next run, so that the recovery is the same as for every other fleet-state file.
11. As a fleet maintainer who edits the `docs/agents/triage-labels.md` table after the map was cached, I want the next run to re-derive from the new table, so that the committed file wins over the cache.
12. As the run-team controller, I want the Label map derivation step to run in phase 0 before the pre-flight and before any claim, so that no member ever runs against an absent or stale map.
13. As the run-team controller, I want to type the mapped string wherever a runbook names a role in a `gh` command, so that relabel-by-cause, filing and claim release work on a remapped repo.
14. As a solo developer running `/next-ticket`, I want the candidate list and the claim to use the map, and the derivation step (question included) to run before the first query, so that the solo flow matches the fleet's.
15. As a fix-applier running `/review-and-fix` standalone, I want deferrals filed under the repo's `needs-triage` string, so that triage finds them.
16. As a fix-applier or finisher dispatched by the fleet, I want to read the map and never be asked anything, so that a member with no channel to the maintainer never stalls on a question.
17. As a merge bot, I want to read the repo's `ready-to-merge` string from the map in every poll and gate, so that a renamed merge label still queues PRs.
18. As a cockpit operator, I want the pool column and the READY state to read the mapped strings, so that the cockpit shows the same work the controller sees.
19. As a plugin maintainer, I want every script that reads or writes a label to resolve the role through one shared reader, so that there is one place a role becomes a string.
20. As a plugin maintainer, I want a script run where no map exists to refuse and name the derivation step, so that a remapped repo can never silently read as "no work".
21. As a plugin maintainer, I want every map writer — the derivation step and `set` — to refuse a string that cannot be queried or typed safely (a double quote, a backslash, `$`, a backtick or a comma, GitHub's length limit, two roles sharing one string), so that neither the Shortlist query, a `gh` label flag nor a command prose has a member type can be broken by a derived or confirmed string.
22. As a plugin maintainer, I want the five `wayfinder:*` and the three release labels left as they are, so that this change covers the labels the fleet owns and nothing another skill owns.
23. As a triage-skill user, I want the fleet's reading of `docs/agents/triage-labels.md` to follow the skill's own rule ("when a skill mentions a role, use the string from this table"), so that the two agree by construction.
24. As a maintainer of this repository, I want its own run to derive the identity map with no question, so that dogfooding is unchanged.
25. As a fleet maintainer whose tracker has both `onhold` and `on-hold`, I want to be asked which one is the hold label, with `onhold` suggested, so that the fleet never silently picks one and pulls tickets frozen under the other.
26. As a fleet maintainer who answered the question once, I want a later re-derivation (after a table edit) to keep my answers while their labels still exist, so that I am asked once.
27. As a fleet maintainer whose table spells a label `Ready-For-Agent` while the tracker has `ready-for-agent`, I want the row accepted without a question and the map to hold the tracker's spelling, so that every script's comparison against what `gh` returns matches.

## Implementation Decisions

**D1. Vocabulary (two glossary entries, `CONTEXT.md` § Consumer repo).**
- *Label role*: a name the fleet's scripts and runbooks use for a label's meaning — the five triage roles plus `in-progress`, `onhold`, `ready-to-merge`. A role is never typed into a `gh` command; its name is also its default string. Avoid: label, canonical label, constant.
- *Label map*: the fleet-state record mapping every Label role to the string the consumer's tracker uses, derived from the repository's triage-label table and its live label list, confirmed by the maintainer where derivation is uncertain, read by scripts and runbooks. Absent means "derive", never "infer". Avoid: label config, vocabulary file, alias, `labels.json` (as a term).

**D2. Scope: the eight roles.** `wayfinder:*` stays literal (mandated by the external `/wayfinder` skill; negating an absent label is a measured no-op). `patch`/`minor`/`major` stay literal (release segments; the finisher already answers `undefined-in-repo` from the live list). Exactly one string per role — no aliases, no second spelling.

**D3. The cache.** `.fleet/labels.json`, resolved through the shared fleet-dir resolver like the Recipe cache, so a worktree and the main checkout name the same file. Content: `derivedAt` (ISO time), `table` (what the triage-label table said when derived: `present` and its `rows`, so a changed table is detected by comparison), `roles` (all eight role→string, each in the tracker's own spelling — D5), `origin` per role: `table` | `default` | `maintainer`. Gitignored with the rest of `.fleet/`; never committed; never written by hand. *Amended (#3930): a `table.rows` value is a string, or an array of strings — a role's string when the table has one distinct string for it, and the array of its distinct strings, in file order, when the table has two or more rows with different strings for it, compared exactly, case included. A role repeated with the same string is that one string, not an array. A role with no non-empty row is absent from `rows`. The array form is what lets a change to a second row for a role show when the cached table is compared with the current one.*

**D4. One module, three verbs, plus a reader.** A new script module `label-map` (the Resolver reaches it like every sibling) owning the cache's format:
- `ensure` — the **Label map derivation step**. Reads the cache and the live label list (D5). The cache is valid when it parses, holds all eight roles, passes D8, its `table` equals the table now in the repo, and every mapped string exists live (D5) → prints the map, exit 0, writes nothing. Otherwise derives (D5), the cache as an input: every role certain and the map passes D8 → writes the cache, prints the map, exit 0; the table breaks D8 (D5) → exit 1 naming each role, the rule and the fix (D5), writes nothing, creates nothing — the fault is in the committed table, and a question could only offer the same string back; otherwise any role uncertain → prints the question payload (D6) and exit 3, writes nothing, creates nothing. Exit 2: not a repository, or `gh` could not answer — the live list is read on every call, so an `ensure` that cannot reach `gh` is exit 2 even with a cache.
- `set [--accept-suggestions] [--create] [<role>=<label> …]` — writes the map from a fresh derivation plus the maintainer's answer: explicit pairs win, `--accept-suggestions` fills every remaining uncertain role with its suggestion, any uncertain role still uncovered — a role with no suggestion (D5) included — is a refusal naming it (exit 1). An explicit pair settles its role before D5's table check, so a role named in a pair never resolves to its default: `set needs-triage=triage` clears the break a `ready-for-human`→`needs-triage` row causes, and the answer then carries over (D5); a break left is exit 1, as in `ensure`. Each confirmed string that does not exist live is created with `gh label create <string>` only under `--create` (no colour is passed; an "already exists" answer counts as existing, and the live list is read again so the map stores the tracker's spelling); without `--create` a missing string is a refusal naming it. Writes only when every mapped string exists live, each stored in the tracker's spelling. Exit 0 prints the map.
- `show [<role>]` — prints the mapped string (one role) or the whole `roles` object (no role). Exit 1 with no cache or an invalid one, the message naming `ensure` as the derivation step. Exit 2 unknown role / not a repository.
- The reader is an exported function the scripts import (D9): returns the `roles` object when the cache parses, holds all eight roles and passes D8, or throws a typed error whose message names the derivation step. It never reads the live list. No defaults at read time — the user's ruling.

**D5. Derivation, per role.** Inputs: the table (D7); the live label list (`gh label list --limit 1000 --json name`; a list that fills the limit is exit 2, the capped-list rule every list read here follows); and the cache when it parses (its `roles` and `origin`), whether or not it is otherwise valid — except that a cache that breaks D8 carries no answer (its strings still decide which roles are gone).
- *Exists live* ignores case — GitHub matches label names case-insensitively (a `label:"READY-FOR-AGENT"` search returns the `ready-for-agent` issues) and answers "already exists" to a second label differing only in case (reported by `gh label create` users; not measured here, since it needs a write). Whenever a string exists live, the string the map stores is the live label's own spelling, never the table's or the answer's: a table row `Ready-For-Agent` with `ready-for-agent` live is certain and maps to `ready-for-agent`. So the scripts' exact comparisons against names `gh` returns (D9) need no case folding.
- A *near match* is a live label equal to the role's name after lowercasing and dropping every non-alphanumeric character (`on-hold` ≈ `onhold`, `Ready For Agent` ≈ `ready-for-agent`); a *different* near match is one that is not the role's default (ignoring case). A near match D8 rejects, or one that equals (ignoring case) the string a certain role holds, is neither a suggestion nor a candidate; the suggestion order moves on to its next source.
- *Gone*: the cache maps the role to a string that does not exist live — the label was renamed or deleted after the map was cached.

Verdicts, the first that applies:
- the table has a row for the role and its string exists live → *certain*, origin `table`. A table row always wins over a carried answer (Story 11).
- the table has a row whose string is not live, or two rows for the role with different strings → *uncertain*, suggestion the table's string. *Amended (#3945): for a role with two or more different table strings (D3), the suggestion is its first string in file order, in the tracker's spelling when that string is live (as for any table string, "Exists live" above); a live first string does not make the role certain. The role's other table strings are never offered as candidates: a live near match equal (ignoring case) to a string a table row names is neither a suggestion nor a candidate, so D6's `candidates` holds only live near matches that no row names. On `set`, a role an explicit pair settles has its own table row unread (D4): the pair's string takes that row's place in this rule, so the unread row's string can be another role's suggestion or candidate.*
- no row, and the role is gone → *uncertain* (Story 9); suggestion as in the last verdict.
- no row, and the cache holds a `maintainer` answer for the role whose string exists live → *certain*, origin `maintainer`: the answer carries over the re-derivation, so the maintainer is asked once. An answer is not carried — the role is *uncertain*, suggestion as in the last verdict, asked again — when its string (ignoring case) is one another role's table row now names (the table is the newer declaration), or one another role *resolves to as its default*: that role has no row and no carried answer, and its default is its certain string or its suggestion by these verdicts (a role's own name outranks an old answer). Dropping one answer can make its role resolve to its default and so drop another; the rule is applied until nothing more drops, starting with every answer carried.
- no row, the default (the role's own name) exists live, and no different near match is live → *certain*, origin `default`.
- everything else → *uncertain*, suggestion in order: the default when it is live (`onhold` beside `on-hold` suggests `onhold`, `on-hold` a candidate); else the unique live near match; else, with several near matches, the alphabetically first; else the role's default.

Every near match is listed as a candidate. A gone role's suggestion is withheld when it equals the vanished string (ignoring case) — the role then has no suggestion, so `defaults` cannot re-create a label the maintainer renamed or deleted; any other suggestion stands. Certainty never comes from a near match alone: a near match is a suggestion, which is what "ask when not absolutely sure" means.

D8 on the derive path, checked on the verdicts above before any suggestion is withheld or filtered: a table row whose string D8 rejects by its characters or length, two roles whose rows name one string, or a row whose string (ignoring case) another role resolves to as its default — certain or suggested, live or not (a row mapping `ready-for-human` to `needs-triage` while `needs-triage` has no row and no carried answer) — is exit 1. Nothing is written. The message names each role, the rule and the fix: edit the row; for a row naming another role's default, `set <that role>=<label>` also settles it, since a role with a carried answer no longer resolves to its default. A carried answer never causes a break: it is not carried when a row names its string or another role resolves to it as its default.

So no certain string is another role's suggestion or candidate, and no two suggestions are one string: a `defaults` reply never meets `set`'s D8 refusal.

**D6. The question.** `ensure` exit 3 prints one JSON object: `certain` (role→string already settled), `uncertain` (array of `{role, suggestion, origin: "table"|"near-match"|"default"|"gone", candidates: [live near matches], exists: bool, was, claimedBy}`), and `tableFile` (string: the table's path relative to the checkout's top level, the label-map script's table-file constant). `suggestion` is `null`, and `exists` false, exactly when `origin` is `gone` (D5's withheld suggestion); `was` is the cached string, present only when the role is gone; `claimedBy` is `{role, string, by: "table"|"default"}`, present only when the role's carried answer was dropped because another role's table row now names that string (`table`) or another role resolves to it as its default (`default`) (D5). The asking entry point (D11) renders it as one question listing each uncertain role, its suggestion, why (`declared in <tableFile> but not in the tracker` / `near match in the tracker` / `the default and a near match are both in the tracker` / `nothing found — the default, to be created` / `was <was> when cached; gone from the tracker (renamed or deleted?) — name the label to use`, the last for `gone`; any other reason on a role with `was` is prefixed `was <was> when cached, now gone from the tracker; `, and on a role with `claimedBy` is prefixed `your earlier answer <string> is now <role>'s in <tableFile>; ` when `by` is `table`, `your earlier answer <string> is now <role>'s label (its default); ` when `by` is `default`), the alternatives, and ends with: reply `defaults` to accept every suggestion, or name `<role>=<label>` for any you want otherwise — a role with no suggestion must be named; labels that do not exist are created on your confirmation. After writing, the reply tells the maintainer how to make it permanent: add or edit the row in `<tableFile>` (first cell the role, second the string). The plugin never writes that file. *Amended (#3945): the first reason, `declared in docs/agents/triage-labels.md but not in the tracker`, is for an `origin: "table"` entry whose `exists` is false. An `origin: "table"` entry whose `exists` is true is a role with two or more different table strings whose first string is live (a role with one live table string is certain, D5), and its reason is `declared more than once in docs/agents/triage-labels.md with different labels; the first is the suggestion`, which does not claim the string is missing from the tracker. The `candidates` of such an entry are live near matches only; the role's other table strings are not among them (D5). The asking entry point renders it as `declared more than once in <tableFile> with different labels; the first is the suggestion`, and the `was` and `claimedBy` prefixes apply to it as to any other reason (#4008).* *Amended (#3963): `<tableFile>` above stands for the payload's `tableFile` value, which the entry point substitutes when it renders the reason and the permanence instruction; the shipped prose (ADR 0019) never spells the path itself. The step that reads the payload (`phase0.mjs`) does not require `tableFile`.*

**D7. The table.** `docs/agents/triage-labels.md` under the current checkout's top level. The table read is the one whose second header cell, backticks and whitespace stripped, is `Label in our tracker` — the header `/setup-matt-pocock-skills` seeds; any other table in the file is not read (this repository's second table, `Labels that are not triage roles`, has an `onhold` row whose second cell is a description, not a label). In it, a row is any markdown table line whose first cell, backticks and whitespace stripped, is one of the eight role names; the second cell, stripped the same way, is the string (a role with two rows of different strings has both, as D3 records). Header and separator rows never match. The five-row seed `/setup-matt-pocock-skills` writes is read as-is; a consumer may add rows for `in-progress`, `onhold`, `ready-to-merge` and they are honoured the same way. An empty second cell is no row. File absent → `table.present = false`.

**D8. Valid strings.** Non-empty after trimming, at most 50 Unicode code points (GitHub's limit; counted by code point, not UTF-16 unit, so an astral emoji is one), none of `"`, `\`, `$`, `` ` `` and `,`, and no two roles mapping to one string, compared ignoring case (D5). `"` and `\`: the Shortlist query cannot represent them — the existing `--require-label` refusal — and `gh`'s label flags read a value as CSV, where a bare `"` is a parse error. `$` and `` ` ``: prose types a mapped string inside double quotes (D11), where both expand. `,`: GitHub refuses a label name holding it, and `gh`'s `--label`, `--add-label` and `--remove-label` split a value on it. `'` stays valid: trackers spell `wontfix` `won't fix`, D5's near match, and prose never puts a mapped string inside single quotes (D11). `set` refuses otherwise, naming the role and the rule; `ensure`'s derive path refuses the same way (D5), and the reader rejects a cache that breaks it.

**D9. Every script resolves roles through the reader; no caller passes strings.** The scripts that change, and what each does with the map:
- the candidates scan: the exclusion clause, today the static literal `EXCLUDE` that no caller assembles, becomes a function of the map: the mapped `in-progress`, `onhold`, `wontfix`, `needs-triage`, `needs-info` are quoted in `query()` — the call site the `EXCLUDE` comment names as the home of a quote-everything rule, which today quotes only the `--require-label` value — and the five `wayfinder:*` clauses stay literal and unquoted as they are today; the comments at `EXCLUDE` that call it a static literal no caller assembles are rewritten with it. `--require-label` now names a **role** and is resolved through the map — an unknown role is a usage refusal (exit 2); both callers already pass `ready-for-agent`, so neither changes.
- the shortlist, the cockpit's pool gather, the tick's claimed count, the stranded scan: the role they read replaces the constant.
- the board compute, the tick's queued set, the merge gate, the finisher's label script: `ready-to-merge` resolved through the map for every read and the one write.
- the dispositions check: the `needs-triage`/`ready-for-agent` home ordering and the `wontfix` record test compare against mapped strings; the row table keeps roles.
- the three shell scripts (claim, release, drop-merged-label): obtain the string once via `label-map show in-progress` through their sibling-script directory, refuse with its message when it refuses, and use it in every `gh issue edit` and every label scan; their dry-run `would:` lines print the string.
- stderr and receipt text may name the role (`in-progress: still on the issue`); a `gh` argument, a label comparison, and any text written to the tracker that names a label use the string. A record the fleet writes to the tracker and parses back keeps its fixed grammar even where it contains a role name: today only the head record `ready-to-merge-head: <sha>`.

**D10. The pre-flight.** The three per-label rows are deleted and no label row replaces them. The derivation step runs before the pre-flight (D11) and has already checked every mapped string against the live list, so a pre-flight row could not fail after it — and the marker skip would have hidden a later rename from it anyway. The deletion moves the check-set hash, so the first run after this lands checks once more.

**D11. Entry points and the ask.** The Label map derivation step is `ensure`, then — on exit 3 — the question (D6) and `set --create` with the answer, then `ensure` again, which now exits 0.
- `/run-team` phase 0: after the instruments pin and the main-checkout baseline, before the pre-flight. Exit 3 → ask the maintainer and wait; nothing in the run — no pre-flight, no Shortlist, no Pull, no dispatch — proceeds until the map is written. This is the controller's own step, once per run start.
- `/next-ticket`: step 1, before the candidates query. The `gh label create in-progress …  # first time only` line leaves: creation is the derivation step's, on confirmation.
- `/review-and-fix` standalone: before its step 1. Dispatched as a fix-applier, and every other dispatched member (implementers, finishers, the merge bot): never `ensure`, never ask. Each reads every role its prose has it type or compare with `show <role>`, once, before it acts, and uses those strings for the rest of its run; a member whose prose types or compares no role reads nothing. A refusal (any non-zero exit from `show`) ends the member with its family's existing outcome — the fix-applier writes no report and the controller settles it `failed`; the finisher halts with cause `other`; the dispatched merge bot holds no grace and reports every PR its dispatch queued `refused` with reason `label-map-refused`; the top-level `/run-merge-bot` prints what `show` printed and stops — and the member never types the role name in place of the string.
- At every entry point that runs `ensure`, exit 1 (a D8 break in the table, with its fix) and exit 2 (no repository, or `gh` unreachable) are shown to the maintainer and stop the flow; neither is a question.
- The merge bot's monitor shell snippet and every `gh … --label` in shipped prose read the string via `label-map show <role>` or type the string the map printed; the prose rule stated once near the top of each shipped runbook/command/agent that names a label: *label names in this file are roles; the Label map gives the string to type; a member never derives the map.*
- A command in prose that takes a mapped string carries it inside double quotes, as `"<role string>"` — never inside single quotes, never bare — and the file says once that `<role string>` is what `show <role>` prints. D8 refuses every character double quotes expand; `'`, which D8 leaves valid, would break a single-quoted span, and a space splits a bare word.

## Out of Scope

- `wayfinder:*` and `patch`/`minor`/`major` (D2).
- Writing or creating `docs/agents/triage-labels.md` in a consumer repo; the plugin reads it only.
- Aliases — two strings for one role — and a configurable *set* of roles; the eight are fixed.
- Deriving the map by agent reasoning (a deriver member): the sources are a table of known shape and a label list, so a script derives and the maintainer decides; no new agent.
- Live re-validation on every script read: the derivation step checks every mapped string against the tracker once per entry-point start. A label renamed or deleted mid-run is caught at the next start; until then a write against it fails as its own `gh` error, and a read of it (the Shortlist's `ready-for-agent`) answers "no work".
- Any change to which role is written where (D13).

## Further Notes

- This repository derives the identity map with no question: its table is the five identity rows and all eight labels exist, so the first run after this lands is the dogfooding check.
- `ensure` reads the live label list once per call — on the cached path to check every mapped string, on a derivation to derive from it — so the network cost is one `gh label list` per entry-point start and one per `set`, in place of the three `gh label list --search` calls the pre-flight makes today on a fresh marker.
- The Recipe precedent decides the shape: cache under `.fleet/`, scripts read and refuse when absent, derivation is an explicit phase-0 step. Two differences are deliberate. Who decides when derivation is uncertain — the maintainer, by a question, not a deriver agent — because a label vocabulary is a convention only the maintainer can rule on. And the cache is checked against the tracker on every `ensure`, where the Recipe cache is trusted until its inputs change, because a label renamed in the tracker changes no file the fleet can see.
